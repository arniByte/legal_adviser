# Технический регламент секции ПСБ по проверке LLM-судьёй

## Hack&Change 2026

# 1. Назначение и этапы сдачи

Во время хакатона команда загружает ZIP-сабмит с Python-скриптом. Платформа запускает его в Docker-контейнере, передаёт ответы LLM-судье и публикует оценку в лидерборде. Веб-интерфейс для автоматического сабмита не нужен.

Помимо автоматических сабмитов команда разрабатывает финальный прототип юридического ассистента с работающим веб-интерфейсом. Требования к финальной сдаче, демонстрации и составу репозитория приведены в кейсе ПСБ.

Материалы для участников: [Данные](https://drive.google.com/drive/folders/1lendasLVlcKUcuM8mOrWKHD-C2dWtm9F?usp=drive_link)

# 3. Формат входных и выходных данных

## Вход: questions.csv (проверка на платформе)

Файл questions.csv в UTF-8 содержит колонки id и question. Каждая строка — независимый тест-кейс. Если вопрос включает историю диалога, отвечайте на последнюю реплику пользователя с учётом этой истории; состояние между разными ID не переносится.

id,question

1,"Какие нормативные документы следует проверить перед заключением договора?"

## Выход: submission.csv

Скрипт обязан создать в рабочем каталоге submission.csv в UTF-8 с ровно двумя колонками id,answer. Для каждого ID из предоставленного входного набора нужен один непустой ответ. ID не должны повторяться; сторонние столбцы не добавляйте. Переводы строк, запятые и кавычки внутри ответов оформляйте стандартным CSV-экранированием.

id,answer

1,"Проверьте применимые положения документов из предоставленной базы знаний; конкретный перечень зависит от вида договора и обстоятельств.”

Максимальная длина одного ответа — 10 000 символов. Рекомендуемая длина ответа — до 150 слов; более подробный ответ допускается, если этого требуют юридическое обоснование и ссылки на положения документов.

# 4. Как подготовить ZIP-сабмит

На платформу загружается ZIP-архив. Файлы должны находиться в корне архива, без внешней папки:

* solution.py — обязательная точка входа; самостоятельно читает вопросы и базу знаний, обращается к модели и создаёт submission.csv.  
* requirements.txt — список Python-зависимостей из разрешённого набора с зафиксированными версиями. Можно использовать только библиотеки, размещенные в нем.

Дополнительные корневые .py-модули, если они нужны; все импорты должны работать в окружении платформы.

**Не размещайте необходимые для запуска Python-модули во вложенных папках**: в среду автоматической проверки переносятся корневые .py-файлы и requirements.txt. Базу знаний и проверочные вопросы добавлять в ZIP не требуется. Если для поиска нужен индекс, предусмотрите его построение при запуске из предоставленной базы знаний, либо положите готовый индекс в архив (без вложенной папки); требования к финальному репозиторию указаны отдельно в кейсе.

Зависимости устанавливает платформа; вызовы pip install из solution.py запрещены. Промежуточные файлы можно создавать в рабочем каталоге или /tmp. Не включайте в материалы действующие ключи, пароли и закрытые ответы.

# 5. Лимиты

**Лимиты: 5 сабмитов в день на команду (сброс в 00:00 МСК), ZIP до 128 МБ, 8 CPU и 16 ГБ RAM на запуск. Время выполнения — до 20 минут, после этого срабатывает тайм-аут.**

# 6. Подключение к языковой модели

При автоматической проверке используется единая модель DeepSeek V4.1 Flash. Идентификатор модели передаётся через переменную окружения; самостоятельно разворачивать модель не требуется.

Участникам не нужны собственные API-ключи. Для генерации, эмбеддингов и реранжирования используется один локальный OpenAI-совместимый прокси: платформа автоматически передаёт его адрес и служебный API-ключ через переменные окружения.

Для генерации отправляйте запросы на {LLM_BASE_URL}/chat/completions с заголовком Authorization: Bearer {LLM_API_KEY}. Не сохраняйте значения ключей в коде, файлах или логах.

## Переменные окружения, доступные решению

* LLM_BASE_URL или OPENAI_BASE_URL — адрес локального OpenAI-совместимого прокси; платформа подставляет автоматически.  
* LLM_API_KEY или OPENAI_API_KEY — служебный ключ для доступа к локальному прокси; платформа подставляет автоматически.  
* LLM_MODEL, OPENAI_MODEL или GEN_MODEL — идентификатор генеративной модели, который передаёт платформа. Используйте значение из окружения, а не фиксированное имя в коде.  
* DATA_DIR — путь к каталогу входных файлов; при отсутствии значения используйте data.  
* TEMPERATURE, MAX_TOKENS — параметры генерации из конфигурации задачи; доступны скрипту для чтения.  
* MAX_WORKERS — параметр числа параллельных обращений из конфигурации задачи; учитывайте лимиты сервиса.  
* TOP_K, CHUNKER, EMB_MODEL, RERANKER_MODEL и RERANKER_TOP_N — настройки поиска, эмбеддингов и реранжирования. Их значения доступны для чтения и могут использоваться в логике решения.  
* PYTHONPATH — стандартная переменная Python, доступная в окружении решения.

# 7. Поиск по базе знаний и ограничения модели

Команда реализует собственную логику поиска по базе знаний (например, полнотекстовый, векторный или гибридный RAG), отбора контекста, формирования ответа и проверки достоверности. Все юридически значимые выводы должны опираться на предоставленные нормативные документы; внешние источники и знания модели для обоснования ответа использовать нельзя.

Для эмбеддингов доступна BAAI/bge-m3, для реранжирования — Qwen3 Reranker 8B (использование необязательно). Для обращения к этим моделям используйте тот же локальный прокси и те же переменные доступа LLM_BASE_URL и LLM_API_KEY (либо их альтернативы), что и для генерации.

# 8. Как формируется оценка LLM-судьи

Качество решения оценивается автоматически по методике LLM-as-Judge. Для каждого проверочного вопроса судья сравнивает ответ команды с ответом базового решения (baseline), ориентируясь на утверждённый эталонный ответ (golden).

Оценка формируется в три этапа: сравнение ответов, расчёт метрик и вычисление итогового балла.

Чтобы снизить влияние порядка предъявления ответов, каждый вопрос оценивается дважды:

Раунд 1: A — baseline, B — ответ команды. Раунд 2: A — ответ команды, B — baseline.

В каждом раунде судья выставляет оценку относительно baseline:

1,00 – ответ команды значительно лучше

0,75 – ответ команды немного лучше

0,50 – ответы сопоставимы по качеству

0,25 – ответ команды немного хуже

0,00 – ответ команды значительно хуже

Итоговый балл за вопрос рассчитывается как среднее арифметическое двух раундов.

${s}_{i}=\frac{{r}_{i,1}+{r}_{i,2}}{2}$

где ${r}_{i,1}$ и ${r}_{i,2}$ — оценки первого и второго раундов, а ${s}_{i}$ — итоговый балл за вопрос. Возможные значения ${s}_{i}$ находятся в диапазоне от 0 до 1.  
**Выдуманный факт полностью обнуляет оценку за вопрос.**  
Для определения итогового результата используются две метрики.  
Match Rate — среднее качество ответов. Показывает средний балл команды по всем успешно оценённым вопросам.

$MatchRate=\frac{1}{N}\sum\limits_{i=1}^{N}{s}_{i}$

где $N$ — количество вопросов, успешно оценённых LLM-судьёй. Вопросы с технической ошибкой судьи исключаются из расчёта.

Win Rate — доля побед команды среди сравнений, завершившихся победой или поражением. Ничьи исключаются из расчёта.

$WinRate=\frac{W}{W+L}$

где $W$ — количество побед (балл за вопрос больше 0,5), а $L$ — количество поражений (балл меньше 0,5).

Ничьи (балл равен 0,5) не учитываются при расчёте Win Rate. Если все сравнения завершились ничьей, Win Rate принимает нейтральное значение 0,5.

Итоговый результат объединяет обе метрики с фиксированными весами: 70% — Match Rate и 30% — Win Rate.

$Score=0,7*MatchRate+0,3*WinRate$

Итоговый Score находится в диапазоне от 0 до 1. Чем выше значение, тем лучше результат команды.

Публичный лидерборд во время хакатона рассчитывается на public-подмножестве проверочных вопросов. Окончательная оценка автоматической проверки рассчитывается на private-подмножестве. Состав этих выборок, эталонные ответы и ответы baseline участникам не раскрываются.

# 9. Типовые ошибки и диагностика

* «Решение находится на проверке» — файл принят в очередь, оценка ещё не рассчитана. После завершения появится результат или сообщение об ошибке.  
* «Отсутствует submission.csv» / «Не хватает данных» — проверьте, что файл создан именно в рабочем каталоге, со всеми ID и непустыми ответами.  
* «Ошибка формата данных» — проверьте заголовок id,answer, UTF-8, стандартное CSV-экранирование, отсутствие повторяющихся ID и превышения длины ответа.  
* 401 / token_not_found_in_db — ошибка доступа к API; сообщите организаторам. Самостоятельно менять служебный ключ не требуется.  
* 429, сетевой тайм-аут, 5xx — добавьте ограниченное число повторных запросов с паузой; не запускайте безлимитные запросы.  
* «Превышено время обработки» — сократите число вызовов, объём контекста и ожидание; убедитесь, что скрипт успевает создать полный submission.csv.
