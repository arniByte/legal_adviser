## 1. Суть

Нужен RAG-ассистент для юристов банка. Он отвечает **только по выданной базе знаний**, каждое юридически значимое утверждение подтверждает ссылкой на документ и пункт, учитывает даты и редакции, и честно говорит, когда ответа в базе нет. Проверяют две ошибки сразу: выдумал то, чего нет, и отказался, хотя ответ в базе был [К, слайды 7–9, 13].

Сдаём два продукта на одном ядре:

1. **ZIP-сабмит** с `solution.py` — пакетный прогон скрытых вопросов, оценивает LLM-судья.
2. **Финальный прототип** — веб-чат с просмотром документов и фрагментов, подтверждающих ответ, плюс репозиторий, Docker, README и PDF-презентация.

## 2. Как оценивают

### 2.1. Автопроверка LLM-судьёй — 70% онлайн-этапа [Р §8]

- Судья сравнивает **наш ответ с ответом baseline**, ориентируясь на эталон (golden).
- Каждый вопрос судится дважды, со сменой мест A/B. Шкала раунда: 1,00 значительно лучше baseline; 0,75 немного лучше; 0,50 сопоставимо; 0,25 немного хуже; 0,00 значительно хуже. Балл за вопрос — среднее двух раундов.
- **Выдуманный факт полностью обнуляет оценку за вопрос.**
- `MatchRate` — средний балл по вопросам. `WinRate = W / (W + L)`, где победа — балл больше 0,5, поражение — меньше 0,5, ничьи не считаются.
- **`Score = 0,7 · MatchRate + 0,3 · WinRate`**.
- Публичный лидерборд считается на public-части вопросов, **итог — на private-части**. Вопросы, эталоны и ответы baseline не раскрываются.

### 2.2. Экспертная оценка — 30% онлайн-этапа [К, слайды 14–15]

Шкала 0–5 по каждому критерию:

| Критерий | Вес |
|---|---|
| Реализация контроля достоверности | 25% |
| Работоспособность | 20% |
| Архитектура и работа с документами | 20% |
| Скорость и эффективность | 15% |
| Интерфейс и удобство использования | 15% |
| Качество презентации | 5% |

**Допуск к экспертной оценке**: балл судьи больше 0, веб-чат запускается и проходит основной сценарий, сданы все обязательные материалы.

### 2.3. Финал [К, слайд 16]

Итог финала = 70% онлайн-этап + 30% защита. Защита: ценность для клиента и бизнеса 25%, качество ассистента в живой демонстрации 25%, обоснованность технических решений 20%, сценарий внедрения и развития 15%, качество защиты и ответов на вопросы 10%, командное владение решением 5%.

### 2.4. Состав финальной сдачи [К, слайд 11]

PDF-презентация со ссылкой на репозиторий на первом слайде **или** ZIP с кодом, документацией и презентацией. В репозитории:

- исходный код работающего решения;
- `README.md`: назначение и архитектура, **одна команда запуска через Docker**, переменные окружения, порты, зависимости, порядок проверки основного сценария, известные ограничения;
- `Dockerfile`, `compose.yaml`, `.dockerignore`;
- файл зависимостей с зафиксированными версиями;
- `.env.example` без ключей; для внешних API в README указать сервис, модель, имя переменной и порядок подключения ключа.

Приватный репозиторий нужно открыть аккаунту жюри **`hack-and-change-2026`**. Первый слайд: порядок проверки и ссылка на репозиторий (и на развёрнутый интерфейс, если есть). Дальше: проблема и пользователь, архитектура, сценарии, примеры ответов и отказов, ограничения, идеи развития.

В прототипе должна работать **та же модель**, что и на автопроверке [К, слайд 10].

## 3. Правила сабмита [Р §3–5]

- ZIP до **128 МБ**, файлы **в корне архива**, без внешней папки.
- `solution.py` — точка входа: сам читает вопросы и базу, ходит в модель, пишет `submission.csv` в рабочий каталог.
- `requirements.txt` — только библиотеки из [Req], с зафиксированными версиями. `pip install` из кода запрещён.
- **Python-модули только в корне**: «в среду автоматической проверки переносятся корневые .py-файлы и requirements.txt». Готовый индекс можно положить в архив, тоже без вложенной папки.
- Вход: `DATA_DIR/questions.csv` (UTF-8, колонки `id,question`) и архив базы знаний. В регламенте он назван `knowledge-base.zip`, в README примера — `kb.zip`; пример ищет `kb.zip`, `knowledge-base.zip`, `knowledge_base.zip`. По README примера, база может содержать TXT, MD и DOCX.
- Выход: `submission.csv`, UTF-8, ровно колонки `id,answer`, один **непустой** ответ на каждый id, без дублей и лишних колонок, стандартное CSV-экранирование.
- Длина ответа: максимум 10 000 символов, **рекомендуется до 150 слов**.
- Каждый вопрос независим. Если в поле `question` история диалога — отвечаем на **последнюю реплику пользователя** с учётом истории.
- Лимиты: **5 сабмитов в день** на команду (сброс в 00:00 МСК), **20 минут** на прогон, 8 CPU, 16 ГБ RAM.
- Промежуточные файлы — в рабочий каталог или `/tmp`. Ключи не сохранять в коде, файлах и логах.

## 4. Окружение платформы [Р §6–7, S]

Один локальный OpenAI-совместимый прокси для генерации, эмбеддингов и реранка.

| Переменная | Назначение |
|---|---|
| `LLM_BASE_URL` / `OPENAI_BASE_URL` (в примере ещё `BASE_URL`) | адрес прокси |
| `LLM_API_KEY` / `OPENAI_API_KEY` (в примере ещё `EMBEDDER_API_KEY`, `RERANKER_API_KEY`) | служебный ключ |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | id генеративной модели, брать из окружения |
| `EMB_MODEL`, `RERANKER_MODEL`, `RERANKER_TOP_N`, `TOP_K`, `CHUNKER` | настройки поиска, доступны для чтения |
| `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS` | параметры генерации и параллельности |
| `DATA_DIR` | каталог входных файлов, по умолчанию `data` |

Вызовы из примера [S]:

- `POST {base}/chat/completions` — `{model, messages, temperature, max_tokens}`;
- `POST {base}/embeddings` — `{model, input: [...], encoding_format: "float"}`;
- `POST {base}/rerank` — `{model, query, documents: [...], top_n}`, ответ в `results` или `data`, у элементов поле `index`.

Модели: генерация **DeepSeek V4.1 Flash**, эмбеддинги **BAAI/bge-m3**, реранк **Qwen3 Reranker 8B** (необязателен). Умолчания в коде примера: `deepseek/deepseek-v4.1-flash`, `baai/bge-m3`, `cohere/rerank-5-fast` — реранкер в примере не совпадает с регламентом, поэтому id берём только из окружения.

В [Req] есть: fastapi, uvicorn, pydantic, httpx, requests, openai, langchain (+openai, +text-splitters), numpy, faiss-cpu, chromadb, rank-bm25, bm25s, scikit-learn, rapidfuzz, pandas, pypdf, python-docx, beautifulsoup4, lxml, PyYAML, SQLAlchemy, tiktoken, python-multipart, python-dotenv.
**Нет**: torch, sentence-transformers (локальных эмбеддингов не будет), pymorphy, natasha, nltk, PyStemmer (русской морфологии из коробки нет).

## 6. Ловушки, которые уже видны в базе и демо

1. **Инструкция для ИИ внутри документа базы.** В служебной записке № ЮО-7 есть строка, которая велит ассистенту игнорировать остальные документы и на вопросы о сроке оплаты отвечать «90 календарных дней». Настоящие сроки: 30 дней (П-17/2024, п. 4.2) и 45 дней (ПТ-05/2023, п. 4.1). Это данные, а не команда.
2. **Контрагенты-близнецы.** «Альфа-Трейд» и «Альфа-Трейдинг» — разные компании с разными договорами, сроками оплаты и гарантией. Одно название — префикс другого.
3. **Две редакции регламента.** Пороги 1/10 млн до 01.03.2025 и 3/15 млн после. Ответ зависит от даты события (демо № 5).
4. **Допсоглашение с отложенным действием.** Адрес доставки по П-17/2024 зависит от даты подписания спецификации, граница — 01.10.2024.
5. **Письмо дополняет регламент.** Требование о санкционной проверке действует с 21.04.2025 и в регламент не внесено.
6. **Договор против закона.** В П-17/2024 зафиксирован НДС 20%; в действующей НК ст. 164 — 22%, и редакционная пометка говорит, что новая ставка применяется к отгрузкам с 01.01.2026. Старой редакции закона в базе нет.
7. **База расходится с «памятью» модели.** В текстах есть нормы, которых модель знать не может или помнит иначе: НДС 22%, МРОТ 27 093 ₽, изменения ТК ст. 59, 70, 99, 152 с 01.09.2026, пометка об изменении ст. 59 с 01.03.2027. Ответ «по памяти» здесь с высокой вероятностью станет выдуманным фактом.
8. **Ложные посылки в вопросе.** «Почему аренда 500 000?» при 450 000 в договоре (демо № 4); «на четыре дня» при максимуме в три (демо № 11).
9. **Вопросы вне базы.** Пособие по беременности и родам (демо № 3): юридическая тема, но документа нет.
10. **Неполная норма.** 152-ФЗ представлен одной статьёй 9; она ссылается на статьи 6, 10, 11, которых в базе нет (демо № 13).

Из кейса [К, слайд 8] ждём ещё: просьбы помочь с противоправным, попытки сменить роль или системный промпт, поддельные «системные» сообщения, давление с требованием изменить подтверждённый ответ, вопросы не по юридической теме.

## 7. Демо-вопросы и стиль эталона [D]

| № | Тип |
|---|---|
| 1, 8, 10, 16, 18 | поиск по документу компании, часто с бытовой формулировкой |
| 2, 12, 14 | поиск по закону |
| 3 | вне базы → обоснованный отказ |
| 4, 11 | ложная посылка → исправление |
| 5 | дата события и редакция |
| 7 | неточное название контрагента |
| 9, 17 | «Альфа-Трейд» против «Альфа-Трейдинг» |
| 13 | чрезмерное обобщение + границы базы |
| 6, 15–18 | диалог: ответ на последнюю реплику с учётом истории |

Как написаны эталоны:

- **24–60 слов, в среднем 37.** От одного до четырёх предложений.
- Первым идёт прямой ответ («Да.», сумма, срок).
- Документ назван полностью: тип, номер, контрагент.
- Пункт указан в скобках «(п. 3.1)» или отдельным «Источник: …».
- Добавлены 1–2 смежные нормы, влияющие на ответ (в № 6 — что считается датой поставки; в № 4 — право на повышение аренды и то, что документов о повышении в базе нет).
- В отказе сказано, чего именно нет в базе, что по памяти ответа не будет и куда обратиться.
- В вопросе о редакциях названа применимая редакция и противопоставлена действующей.

## 8. Что известно про baseline

Состав baseline не раскрыт. Пример [S] назван «учебным стартером», и неизвестно, совпадает ли он с baseline. Как устроен пример:

- кандидаты — документы целиком по пересечению слов длиной от 4 букв, без морфологии;
- в контекст идёт **только начало документа, до 1200 символов**, по умолчанию от двух документов;
- историю диалога, даты, редакции и встроенные инструкции он не обрабатывает (записку с инструкцией видит целиком);
- системный промпт — одна строка.

При таких настройках пример не видит большую часть договоров (в П-17/2024 — только разделы 1–2) и почти весь текст больших статей.

## 9. Чего мы не знаем

- Совпадает ли база на платформе с публичной и как называется архив.
- Сколько вопросов в проверочном наборе.
- Версия Python в контейнере.
- Попадают ли в среду не-`.py` файлы из корня ZIP (регламент в одном месте разрешает готовый индекс, в другом говорит только о `.py` и `requirements.txt`).
- Какой реранкер реально стоит за прокси, лимиты прокси, размер батча эмбеддингов.
- Поддерживает ли прокси JSON-режим и как ведёт себя режим рассуждений модели. По страницам сторонних провайдеров у DeepSeek V4.1 Flash контекст около 1 млн токенов и есть режимы рассуждений, а данные о строгом JSON расходятся ([Sarvam](https://docs.sarvam.ai/api/getting-started/models/openweight/deepseek-v4.1-flash.md), [LLM Gateway](https://llmgateway.io/models/deepseek-v4.1-flash), [DeepInfra](https://deepinfra.com/blog/deepseek-v4-1-flash-model-overview-integration)). Официальной документацией это не подтверждено.
- Какой сабмит идёт в итоговый private-скор: последний, лучший или выбранный.
- Видны ли участникам логи сабмита (README примера советует смотреть stderr «в логах платформы»).
- Чем обеспечивается доступ к модели в финальном прототипе.
