# Сравнение версий и откат

Исходный baseline — commit `1b8b4bb1fea97497a1066fe62c5d97adee37901f`.
Новый кандидат пока не получил подтверждённого измерения качества на реальном API или платформе.

## Сборка

Из корня репозитория, без переключения ветки и без изменения рабочих файлов:

```bash
python scripts/build_submission.py --ref 1b8b4bb1fea97497a1066fe62c5d97adee37901f --output dist/baseline-1b8b4bb.zip --smoke
python scripts/build_submission.py --output dist/candidate-working.zip --smoke
```

Вторая команда включает текущие изменения в `submission/`. Для сравнения зафиксированных
версий сначала закоммитьте кандидата в рабочей ветке, затем соберите его через `--ref HEAD`
с отдельным `--output`. `--ref` читает файлы и разрешённые зависимости из указанного commit;
`main`, индекс Git и рабочая ветка остаются на месте. Без аргументов по-прежнему собирается
`dist/submission.zip`.

Рядом с ZIP появляется `<имя>.zip.manifest.json`: SHA commit, признак и список изменённых
файлов для working tree, SHA-256 модулей, списка разрешённых зависимостей, архива и текущих
публичных входных данных, версия Python. Значения переменных окружения не записываются.
Сам manifest не входит в сабмит. ZIP имеет фиксированные порядок, время и права файлов;
повторная сборка одного исходного содержимого в том же окружении даёт одинаковые байты.
Если исходники скачаны без `.git`, обычная сборка работает, но Git-состояние неизвестно.

**`--smoke` всегда использует текущие публичные demo-вопросы и базу из `data/`, даже с `--ref`.**
Он обращается к локальной заглушке API: проверяет запуск и формат CSV, а качество юридических
ответов и совместимость с реальным прокси этим не измеряются.

## Сравнение на реальном API

Сохраните оба ZIP и manifest. Прогоните оба артефакта на одном зафиксированном наборе
вопросов и одной базе, с одинаковыми моделями, настройками генерации, лимитами и
параллельностью. Используйте отдельные рабочие каталоги и одинаковое состояние кешей.
Ключи передавайте только через окружение. В отчёте укажите SHA версий и входных данных,
идентификаторы моделей и параметры; секретные значения и закрытые вопросы не публикуйте.

Для локальных запусков ядра используйте уникальные метки, например:

```bash
python eval/run_eval.py --devset eval/holdout.jsonl --baseline both --repeats 2 --label candidate-holdout-01
python eval/run_eval.py --compare baseline-holdout-01 candidate-holdout-01
```

Baseline должен быть сгенерирован исходным ядром из сохранённого commit, а кандидат —
новым, на тех же входах. Новый скрипт оценки и один промпт судьи используйте для оценки
обоих наборов сохранённых ответов; сравнение разных версий судьи смешивает причины изменения.
Исторический baseline не записывал все хеши: такой отчёт явно укажет неизвестное происхождение.
Повторная оценка `--answers <метка>` создаёт новый каталог; существующий прогон не заменяется
без явного `--overwrite`. `--compare` работает без API и считает разность только на общих
успешно оценённых вопросах с неизменными эталонами и ответами baseline.

`eval/holdout.jsonl` содержит 24 новых сценария по публичной базе с ожидаемыми источниками.
Набор составлен агентом и требует ручной юридической проверки. Не используйте его для
подбора промпта или весов поиска; ограничения описаны в `eval/holdout.README.md`.

Сравнивайте ответы попарно по одним ID: корректность вывода и ссылки на подтверждающее
положение, полноту, ложные отказы, неподтверждённые выводы, ошибки API, время и число вызовов.
Отдельно проверьте даты и редакции, похожих контрагентов, ошибочные посылки, диалоги и
недостаток сведений. Повторные прогоны судьи меняйте местами по порядку предъявления ответов;
сохраняйте разбор регрессий. Локальный `Score` не равен результату закрытой проверки.

Принимать кандидата как улучшение можно после реального сравнительного прогона:
выигрыш воспроизводится, превышает наблюдаемый разброс, обязательные сценарии не
ухудшились, весь пакет укладывается в регламент. Прошедшие тесты и smoke сами по себе
не доказывают прирост качества. Если разницы нет или она в пределах шума, baseline сохраняется.

## Откат

Для сабмита используйте сохранённый `dist/baseline-1b8b4bb.zip`, предварительно сверив его
SHA-256 с manifest. Его можно заново собрать командой выше из точного baseline commit.
Не пересобирайте baseline из текущего working tree под прежним именем.

Для отката кода создайте обычный `git revert` конкретного feature commit в рабочей ветке
и проведите проверки перед PR. Не используйте `reset`/force-push для общей `main`.
Сохранённые baseline-артефакты и результаты измерений не перезаписывайте.

## ML

Эмбеддинги BAAI/bge-m3, реранкер Qwen3 и генерация DeepSeek уже используют ML.
Следующий проверяемый эксперимент — калибровка весов поиска по разметке
«вопрос → подтверждающие документы и положения». Веса подбираются офлайн;
во время сабмита используется компактный расчёт, без обучения и замены разрешённых моделей.

Сначала нужна разметка с трудными отрицательными примерами: другой контрагент,
похожий пункт, прежняя редакция. Перефразировки одной задачи должны оставаться
в одной группе при разделении train/validation/test. Демо и примеры промпта
не являются независимым test. Текущих 68 известных примеров недостаточно,
чтобы заявлять обобщение или качество вероятностного классификатора отказов.
Отдельная обученная модель в этот кандидат не добавлена.
