# Как сдавать: сабмиты и финальный комплект

Сдача идёт в два этапа, и это **два разных продукта**. Первоисточники: кейс (`materials/case_psb_legal_assistant.pdf`, слайды 10–11, 14–16) и техрегламент (`materials/tech_reglament.md`).

| | Автоматический сабмит | Финальная сдача |
|---|---|---|
| Когда | в течение хакатона, до 5 раз в день | один раз, в конце; после дедлайна версия фиксируется |
| Что загружаем | ZIP со `solution.py` | PDF-презентацию со ссылкой на репозиторий **или** ZIP с кодом, документацией и презентацией |
| Кто оценивает | LLM-судья | эксперты |
| Вес в онлайн-этапе | 70% | 30% |
| Веб-интерфейс | не нужен | обязателен |

Итог онлайн-этапа = 0,7 × балл судьи + 0,3 × экспертная оценка. К экспертам допускают, только если балл судьи больше 0, веб-чат работает и сданы все материалы.

## Часть 1. Автоматический сабмит

### Что делает платформа

1. Распаковывает ZIP в Docker-контейнер (8 CPU, 16 ГБ, лимит 20 минут), ставит зависимости из нашего `requirements.txt`.
2. Кладёт в каталог `DATA_DIR` файл `questions.csv` (`id,question`) и архив базы знаний.
3. Запускает `solution.py`. Адрес API, ключ и названия моделей передаёт через переменные окружения.
4. Забирает `submission.csv` из рабочего каталога.
5. LLM-судья сравнивает каждый наш ответ с ответом baseline, ориентируясь на эталон, в два раунда со сменой мест.
6. Результат на public-части вопросов попадает в лидерборд. **Итог считается на private-части.**

### Как собрать и отправить

```bash
python scripts/build_submission.py --smoke
```

Получится `dist/submission.zip`. Скрипт сам проверяет:

- архив плоский, внутри `solution.py`, модули `la_*.py` и `requirements.txt`;
- зависимости — только из разрешённого списка, с теми же версиями;
- нет `pip install` и строк, похожих на ключи;
- размер меньше 128 МБ;
- полный прогон на заглушке API даёт корректный `submission.csv` (`id,answer`, все id, непустые ответы до 10 000 символов).

Дальше — загрузить `dist/submission.zip` на платформе кнопкой сабмита. В архив **не нужно** класть вопросы, базу знаний, `.env`, README.

### Что смотреть после сабмита

Наш `solution.py` пишет в stderr диагностику — только названия и агрегаты, без ключей и без текстов вопросов:

| Строка лога | Что из неё узнаём |
|---|---|
| `env set: …` | какие переменные передала платформа, значения моделей и настроек |
| `data dir: …; solution dir: …` | как называется архив базы; попали ли в среду не-`.py` файлы |
| `questions: N; with dialogue history: M …` | размер набора и долю диалогов, версию Python |
| `knowledge base: … fingerprint …` | совпадает ли база с публичной (у публичной отпечаток `3a0ecc1217a91cae`) |
| `search: lexical + dense` | заработали ли эмбеддинги |
| `first answer: …` | время этапов на первом вопросе |
| `seconds per question p50/p90/max` | укладываемся ли в 20 минут |
| `done: … modes … statuses …` | сколько вопросов ушло в облегчённый режим, сколько отказов, ошибок API, исправлений |

Что делать по итогам:

| Симптом | Действие |
|---|---|
| `modes` содержит `lite` или `skip` | не хватает времени: поднять `LA_MAX_WORKERS` (если нет 429) или отключить реранкер |
| много `429` | снизить параллельность |
| `reranker off` | на прокси другой идентификатор реранкера; это не ошибка, поиск остаётся гибридным |
| отпечаток базы другой | база на платформе отличается; решение рассчитано на это, но стоит перечитать логи про число документов |
| «Отсутствует submission.csv» / «Ошибка формата» | не должно случаться: файл пишется до первого вызова API; смотреть `FATAL` в логе |

### Дисциплина сабмитов

- Лимит — 5 в день, сброс в 00:00 МСК. Сабмит — после `pytest` и `--smoke`, а при наличии ключа — после `eval/run_eval.py`.
- Каждый сабмит записывать в журнал в `docs/STATE.md`: коммит, что изменили, локальные проверки, балл на платформе.
- Не настраиваться на публичный лидерборд: финальный балл считается на других вопросах.
- Неизвестно, какой сабмит идёт в итог (последний, лучший или выбранный) — уточнить у организаторов. До ответа считать, что **последний**, и не отправлять в конце эксперименты.

### Как считается балл

Шкала раунда относительно baseline: 1,0 значительно лучше; 0,75 немного лучше; 0,5 сопоставимо; 0,25 немного хуже; 0 значительно хуже. Балл за вопрос — среднее двух раундов. **Выдуманный факт обнуляет вопрос.**

`MatchRate` — средний балл. `WinRate = W / (W + L)`, ничьи не считаются. `Score = 0,7 · MatchRate + 0,3 · WinRate`.

Следствие: каждое поражение бьёт дважды, поэтому «не выдумать и не отказаться зря» важнее, чем «ответить подробнее».

## Часть 2. Финальная сдача

### Что загружаем

Один из двух вариантов:

- **PDF-презентация**, на первом слайде — ссылка на репозиторий и порядок проверки. Все файлы решения должны быть в репозитории. Приватный репозиторий нужно открыть аккаунту жюри **`hack-and-change-2026`**.
- **ZIP** с исходным кодом, документацией и презентацией в PDF.

После дедлайна версия фиксируется: всё должно быть в ветке по умолчанию.

### Чек-лист комплекта

| Требование кейса | Где у нас | Статус |
|---|---|---|
| Исходный код работающего решения | `submission/`, `app/` | есть |
| README: назначение и архитектура | `README.md`, разделы «Как это устроено» | есть |
| README: одна команда запуска через Docker | `docker compose up --build` | есть, проверено |
| README: переменные окружения, порты, зависимости | `README.md`, «Быстрый запуск» | есть |
| README: порядок проверки основного сценария | `README.md`, «Как проверить основной сценарий» | есть |
| README: известные ограничения | `README.md`, последний раздел | есть |
| `Dockerfile`, `compose.yaml`, `.dockerignore` | корень | есть, образ собирается |
| Файл зависимостей с зафиксированными версиями | `requirements.txt`, `submission/requirements.txt` | есть |
| `.env.example` без ключей | корень | есть |

### Что обязано быть в презентации

Первый слайд: порядок проверки, ссылка на репозиторий, при наличии — ссылка на развёрнутый интерфейс. Дальше: проблема и пользователь, архитектура, сценарии работы, примеры ответов и отказов, ограничения, идеи по развитию.

Исходник презентации — `presentation/deck.html`, сборка — `node presentation/build.js`.

### Как экспертные критерии закрыты в решении

| Критерий | Вес | Что показать |
|---|---|---|
| Реализация контроля достоверности | 25% | проверка кодом под каждым ответом; ложная посылка; редакции; отсеянная инструкция в служебной записке; второй проход перед отказом |
| Работоспособность | 20% | запуск одной командой; сценарий из README; 31 автотест |
| Архитектура и работа с документами | 20% | разбор по структуре, реестр документов, адаптивный контекст, одно ядро на сабмит и чат |
| Скорость и эффективность | 15% | один вызов модели на типовой вопрос; время по этапам в интерфейсе; бюджет времени в пакетном режиме |
| Интерфейс и удобство | 15% | подсветка фрагмента в полном тексте, статус ответа, «Как получен ответ», мобильная вёрстка, тёмная тема |
| Качество презентации | 5% | `presentation/paragraf.pdf` |

### Перед отправкой финала

1. `python -m pytest -q tests` и `python scripts/build_submission.py --smoke` — зелёные.
2. На чистой машине: `cp .env.example .env`, вписать ключ, `docker compose up --build`, пройти сценарий из README.
3. Проверить, что в репозитории нет `.env` и ключей.
4. Слить рабочую ветку в `main`, сделать `main` веткой по умолчанию, открыть доступ `hack-and-change-2026`.
5. Пересобрать презентацию, если менялись цифры; вписать название команды на первом слайде.
6. Загрузить PDF на платформу до дедлайна.
